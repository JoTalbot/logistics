# AI Agent Operating Instructions — AI Logistics OS

## 1. Назначение

`JoTalbot/logistics` разрабатывается как распределённый проект: над одним репозиторием одновременно работают люди и несколько AI-агентов с разных машин, окружений и моделей. Репозиторий является общей точкой истины.

Цель агента — не просто выполнить локальную задачу, а безопасно продолжить общий проект, не потерять контекст и оставить следующему агенту воспроизводимое состояние.

## 2. Обязательное правило: сначала исследование

**Перед КАЖДЫМ существенным шагом работы агент обязан:**

1. Проверить текущий статус проекта в репозитории.
2. Проверить `docs/`, `AGENTS.md`, `STATUS.md`, `ROADMAP.md`, `CHANGELOG.md` и связанные документы, если они существуют.
3. Проверить GitHub на наличие подходящих существующих реализаций, issues, PR, документации и примеров.
4. Выполнить глубокое исследование интернета по текущей задаче: официальная документация, стандарты, актуальные SDK/API, лучшие практики, зрелые open-source проекты и известные ограничения.
5. Проверить наличие подходящего **agent skill / skill.md** в доступных каталогах навыков и в интернете/GitHub. Если подходящий skill найден, агент обязан использовать его либо явно зафиксировать причину, почему его нельзя применить.
6. Проверить, не реализовал ли другой агент уже то же самое или зависимую часть.
7. Только после этого выбрать реализацию.

Для внешних сервисов приоритет: официальная документация и официальные API. Не использовать обход защит, нарушение ToS или хрупкий scraping как основу продукта.

## 3. Работа параллельно

Агенты должны предполагать параллельную работу по умолчанию.

Перед изменением файла агент обязан:
- проверить его актуальное содержимое;
- проверить недавние изменения/коммиты;
- проверить `STATUS.md` на активную блокировку/зону работы;
- не перетирать изменения другого агента;
- предпочитать небольшие атомарные коммиты.

Если работа затрагивает несколько независимых областей, их следует разделять так, чтобы разные агенты могли работать одновременно без конфликтов.

Не использовать один общий файл как постоянный рабочий журнал всех агентов. Для текущего состояния использовать `STATUS.md`, а подробные исторические логи хранить в `docs/agent-log/`.

## 4. Статус — обязательная часть работы

После каждого существенного шага агент обязан обновить `STATUS.md`.

Статус должен позволять новому агенту за 30 секунд понять:
- что сейчас строится;
- какой этап активен;
- что уже завершено;
- что выполняется сейчас;
- что заблокировано;
- что делать следующим шагом;
- какие файлы изменены;
- какой агент/машина выполняет работу;
- какие решения приняты;
- какие внешние источники/skills были исследованы.

Минимальный формат записи:

```text
CURRENT_STEP: <краткое имя шага>
STATUS: <planned|researching|implementing|testing|blocked|done>
AGENT: <идентификатор агента>
MACHINE: <машина/окружение, если доступно>
STARTED: <ISO-8601>
UPDATED: <ISO-8601>
SCOPE: <что делает агент>
FILES: <затронутые файлы>
RESEARCH: <источники/репозитории/skills>
DECISIONS: <важные решения>
BLOCKERS: <если есть>
NEXT: <следующий конкретный шаг>
```

Агент не должен оставлять `STATUS.md` в состоянии, которое вводит следующего агента в заблуждение.

## 5. Lock/ownership протокол

Если агент собирается выполнять длительную или конфликтную работу, он сначала объявляет ownership в `STATUS.md`.

Пример:

```text
WORK_AREA: docs/architecture/*
OWNER: agent-architecture-01
STATUS: implementing
```

Другой агент не должен молча переписывать эту область. Если изменение необходимо, он должен сначала проверить актуальный статус и согласовать границу работы через репозиторий/issue/PR или выбрать независимую область.

Ownership не является вечной блокировкой: после завершения агент освобождает область.

## 6. Лог каждого агента → его основной skill

Каждый агент обязан вести структурированный рабочий лог в `docs/agent-log/<agent-id>/`.

После каждого существенного шага логировать:
- задачу;
- исследование;
- использованные источники;
- найденные skills;
- команды/действия;
- результат;
- ошибки;
- принятые решения;
- что сработало/не сработало;
- рекомендации следующему агенту.

**Накопленный лог должен периодически превращаться в основной skill данного агента.**

Файл skill агента: `docs/agent-skills/<agent-id>.md`.

Skill должен содержать не секреты и не сырые транскрипции, а извлечённые повторно применимые знания:
- назначение агента;
- проверенный workflow;
- инструменты;
- полезные команды;
- паттерны реализации;
- типичные ошибки;
- критерии качества;
- lessons learned;
- ссылки на первичные источники;
- процедуры восстановления после ошибок.

После значимого нового опыта агент обновляет свой skill отдельным коммитом. Таким образом проект накапливает коллективную память, а не заставляет каждого нового агента заново изобретать велосипед.

## 7. Skills-first

Перед каждым шагом агент должен искать подходящий skill.

Порядок:

1. локальные skills проекта;
2. skills в `docs/agent-skills/`;
3. установленные skills текущего AI-окружения;
4. официальные каталоги skills;
5. GitHub/open-source skills;
6. интернет-поиск.

Если найден подходящий skill — изучить его и следовать ему.

Если найдено несколько skills — выбрать наиболее релевантный и указать выбор в логе.

Если подходящего skill нет — выполнить работу по общим правилам проекта и при наличии повторно применимого процесса создать/обновить skill.

**Нельзя утверждать, что skill существует, если он фактически не найден.**

## 8. Deep Research Gate

Перед реализацией каждой существенной функции агент должен провести исследование минимум по следующим направлениям:

- официальная документация используемых технологий;
- актуальные API/SDK и ограничения;
- минимум несколько релевантных open-source реализаций, когда они существуют;
- безопасность и типовые failure modes;
- актуальные best practices;
- существующие части самого `JoTalbot/logistics`;
- совместимость с архитектурой V1→V10.

Исследование должно приводить к конкретному решению, а не быть формальностью.

## 9. Обязательная синхронизация и немедленный push

**Все логически завершённые изменения должны сразу сохраняться, коммититься и отправляться в GitHub.**

Стандартный цикл:

```text
изменение
  ↓
проверка
  ↓
обновление STATUS.md
  ↓
обновление agent log
  ↓
обновление skill при наличии нового reusable опыта
  ↓
commit
  ↓
push в GitHub
  ↓
проверка удалённого commit
```

Готовая работа не должна оставаться только на локальной машине. Исключение — короткоживущие изолированные промежуточные изменения, которые ещё не являются логически завершённым результатом.

После push агент обязан проверить удалённое состояние и убедиться, что его commit виден другим агентам.

Не выполнять `force push` без явной необходимости и проверки последствий для параллельных агентов.

## 10. Commit discipline

Каждый логически завершённый шаг должен иметь отдельный понятный commit.

Примеры:
- `docs: add distributed agent protocol`
- `docs: add logistics architecture`
- `feat: add opportunity scoring`
- `fix: handle carrier timeout`

Не смешивать несвязанные изменения в одном коммите.

Перед commit проверить:
- конфликт с параллельными изменениями;
- форматирование;
- тесты, относящиеся к изменению;
- документацию;
- обновление статуса и agent log.

## 11. Не считать отсутствие тестов разрешением пропустить качество

Если тесты существуют — запускать релевантные тесты.
Если тестовой инфраструктуры ещё нет — документировать, что именно проверено вручную, и создать план тестирования.

Для финансовых, юридических, security и интеграционных операций применять дополнительные проверки.

## 12. Безопасность

Никогда не помещать в репозиторий:
- API keys;
- passwords;
- access tokens;
- private keys;
- cookies/session credentials;
- персональные данные без необходимости.

Использовать `.env`, secret managers и безопасные настройки окружения.

Не автоматизировать мошенничество, обход ограничений платформ или несанкционированный доступ.

## 13. AI Logistics OS — особые требования

Архитектура должна поддерживать:
- **старт с Украины** и постепенное расширение на Европу и далее;
- DELLA и Lardi-Trans через разрешённые способы интеграции;
- дополнительные рыночные источники, подключаемые постепенно;
- market discovery;
- pricing;
- carrier/client matching;
- negotiation и AI Voice;
- risk/anti-fraud;
- документы;
- dispatch/tracking;
- route и load-chain optimization;
- finance;
- forecasting;
- Trust Graph;
- multi-agent Supervisor;
- AI CEO;
- simulation/shadow mode;
- audit trail;
- human-on-exception;
- multi-tenant масштабирование.

Все ранее согласованные функции и будущие расширения внедряются **поэтапно**, начиная с Украины, без архитектурной привязки ядра к одной стране, бирже или поставщику.

## 14. Human-on-exception

Автономность не означает безусловное выполнение.

Каждое действие должно иметь:
- допустимые лимиты;
- уровень риска;
- confidence;
- возможность эскалации;
- audit trail.

При недостаточной уверенности AI обязан передать решение человеку.

## 15. Handoff между агентами

Перед завершением работы агент обязан оставить:

```text
DONE: <что реально завершено>
VERIFIED: <как проверено>
RESEARCHED: <что исследовано>
FILES: <файлы>
COMMITS: <коммиты>
OPEN_ISSUES: <нерешённые вопросы>
NEXT_STEP: <конкретное продолжение>
```

Следующий агент обязан сначала прочитать этот handoff и актуальный `STATUS.md`.

## 16. Definition of Done

Работа считается завершённой только если:

- решение реализовано или документировано;
- исследование выполнено;
- подходящий skill проверен;
- изменения проверены;
- статус обновлён;
- agent log обновлён;
- lessons learned перенесены в skill при наличии нового повторно применимого опыта;
- следующий шаг понятен другому агенту;
- изменения сохранены в Git;
- commit запушен в GitHub;
- удалённое состояние проверено.

## 17. Главное правило

**Никогда не начинать работу с предположения, что ты единственный агент проекта.**

Сначала исследуй текущую реальность проекта и внешнего мира. Затем действуй. После действия оставь проект в состоянии, в котором другой агент сможет продолжить работу без разговора с предыдущим агентом.

**Любое логически завершённое изменение сразу должно оказаться в GitHub.**
