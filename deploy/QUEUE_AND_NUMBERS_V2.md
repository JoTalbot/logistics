# Независимая очередь и числовая нормализация V2

## 1. Независимое пополнение очереди

Добавлен сервис `enqueuer` (`deploy/llm_enqueue.py`). Он каждые 10 секунд ставит новые сохранённые сообщения в очередь, независимо от длительности inference. Чтение Telegram остаётся в `collector`, обработка — в `normalizer`.

- При первом включении сохраняется правило последних 100 сообщений на источник, затем только новые.
- Вставка защищена от повторов; наличие задачи проверяется по исходному сообщению независимо от версии парсера. Завершённые старые результаты не переобрабатываются автоматически при смене версии.
- Курсор источников и исходные данные не изменяются.
- `telegram_llm_config.enqueued_at` — время последней постановки/проверки; `last_enqueued_count` — число добавленных задач последнего прохода.
- Используется отдельный advisory lock. Падение процесса не теряет сообщения: они уже в PostgreSQL, следующий проход их найдёт.
- Ограниченная роль БД получила только UPDATE двух новых полей heartbeat; доступ на изменение грузов не расширялся.
- На первой проверке сервис догнал накопившиеся сообщения: 123 + 7 задач, непоставленных новых сообщений осталось **0** при остановленном normalizer.

## 2. Нормализация V2

Версия результата: `local-qwen-extract-v2`. Необработанные задачи прежней версии переведены на V2, завершённые результаты V1 сохранены.

### Вес

Числа и единицы извлекаются из исходного текста, а не только из неполной цитаты LLM. Поддерживаются `кг`, `kg`, `килограмм`, `кілограм`, `т`, `t`, `тн`, `тон`, `тонн`, `тонна`, `тонны`, `tons`, десятичная запятая и пробелы-разделители тысяч.

- `22 тон` → `22000 кг`.
- `12 500 kg` → `12500 кг`.
- `20–22 т` → диапазон `weight_min_kg=20000`, `weight_max_kg=22000`; одиночный вес не придумывается.
- При нескольких разных значениях и отсутствии однозначной подтверждённой цитаты значение не выбирается автоматически.
- Нулевые/отрицательные значения не принимаются; необычно большой вес остаётся сигналом для проверки.

### Деньги

- Извлекаются суммы с явной валютой либо с меткой цены/ставки.
- Произвольное число или телефон не считается ценой.
- Поддерживаются USD, EUR, UAH, RUB, UZS, KZT, TRY, PLN, GBP и предусмотренные явные текстовые обозначения.
- `$` без уточнения не определяет национальную валюту — валюта остаётся неизвестной.
- `25 000 грн` → `25000 UAH`; `USD 500` → `500 USD`.
- Неоднозначное `25,000 USD` не превращается молча в 25 или 25000.
- Несколько цен, варианты оплаты и диапазоны требуют проверки; нельзя бездумно объединять их в одну ставку.
- Ставки `/км`, `/т` помечаются отдельно и не принимаются за стоимость всего рейса.

### Границы безопасности

Детерминированное извлечение единицы не доказывает, что вес относится к нужному грузу, а не к автомобилю. То же относится к роли суммы. Все результаты остаются `review_required=true`, без автоматического изменения `loads` и публикации.

Служебные строки вроде `"null"`, `"none"`, `"n/a"` нормализуются в отсутствие значения. Это не приравнивает другие неподтверждённые строки к достоверным данным.

## Проверка числовой части без изменения БД

На 31 прежнем результате (из предыдущей нерепрезентативной выборки) повторно проверены только числовые поля по тем же исходным текстам:

| Поле | Прежний результат | Новая числовая нормализация |
|---|---:|---:|
| Нормализованный одиночный вес | 3 | 15 |
| Сумма | 11 | 6 |
| Однозначная валюта | 0 | 0 |

5 неподтверждённых сумм не прошли новые правила, 9 записей получили сигнал нескольких весов, 11 — нескольких возможных цен. Это проверка заполненности/правил, **не измерение точности**. Старые производственные результаты не перезаписывались.

## 3. Сравнение пакетов 3 / 5 / 10

`deploy/benchmark_batches.py` выбирает одни и те же 10 уникальных коротких реальных объявлений из последних сохранённых сообщений. Источники чередуются; весь набор помещается в контекст без обрезки.

- Пакет 3: 3+3+3+1, четыре запроса.
- Пакет 5: 5+5, два запроса.
- Пакет 10: один запрос.
- Порядок замеров: 5, 3, 10; один проход, общий сервер, без кеша приложения. Внутренний prompt cache Ollama не отключается.
- Контекст одинаковый — 16384; один CPU-поток для inference; лимит одного тестового запроса 360 секунд.
- Измеряются время, полнота ответов по ID, наличие полей и число неподтверждённых полей. Наличие полей не является оценкой правильности.
- Тестовые результаты не записываются в производственные задания.
- Исходники обрабатываются только на сервере, временные входные файлы удаляются после запроса. В отчёте сохраняются ID/хеши для проверки совпадения выборки, но не исходные тексты.

Результат: `/var/lib/logistics/benchmarks/latest.json`. Скрипт `run_benchmark.sh` после завершения выбирает самый быстрый вариант, успешно вернувший все 10 структурированных результатов; если таких нет — консервативно 3. Затем автоматически возобновляет normalizer. Такая настройка не доказывает оптимальность на длинных объявлениях или семантическую точность.

Рабочий таймаут одного запроса уменьшен до 600 секунд. Верхний программный лимит остаётся 100, но рабочий размер выбирается из 3/5/10, а контекстный бюджет может уменьшить его дополнительно.

## Проверки и команды

56 unit-тестов прошли; 4 интеграционных теста прежнего набора пропущены. Применена миграция `0006_enqueue_heartbeat.sql`.

```bash
cd /opt/logistics
docker compose -f deploy/compose.collector.yml logs --tail=20 enqueuer
docker compose -f deploy/compose.collector.yml logs --tail=20 normalizer
docker compose -f deploy/compose.collector.yml exec -T postgres psql -U logistics -d logistics -c \
  "SELECT enqueued_at,last_enqueued_count FROM telegram_llm_config;"
```

Секреты по-прежнему находятся только в `/etc/logistics/llm.env`, не в Git. Настройки других приложений на сервере не изменялись.
