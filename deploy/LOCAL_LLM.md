# Локальная LLM: разбор и нормализация объявлений

## Что включено

Пользователь явно запросил локальный LLM-разбор вместо исключительно regex-подхода. Добавлен **отдельный фоновый контур**, не блокирующий Telegram-сборщик:

`сохранённое сообщение → очередь PostgreSQL → локальная Qwen → проверка JSON и опоры на исходный текст → нормализованный кандидат для проверки`

- Ollama: `http://127.0.0.1:11434`, установленная модель `qwen2.5:1.5b`, digest начинается с `65ec06548149`.
- Используется существующая локальная модель: загрузки моделей, облачных API, обучения и внешней отправки текста нет.
- При активации ставятся в очередь последние 100 сохранённых сообщений каждого источника; затем только новые сохранённые сообщения. Старая история не загружается повторно.
- Оригинальный сборщик и regex-результаты остаются как базовый слой и средство сравнения. LLM-результаты записываются в **telegram_llm_jobs.normalized**, не подменяют `loads` и не публикуются автоматически.

## Выбор модели и ограничения ресурсов

На момент настройки сервер имел 4 CPU, 23 GiB RAM, около 3,4 GiB доступной памяти, без swap. Поэтому выбрана 1.5B, а не 7B. Один последовательный запрос, `num_thread=1`, контекст 4096, максимум 400 выходных токенов, таймаут 150 секунд. Worker ограничен 384 MiB RAM и 0,5 CPU; **эти контейнерные ограничения не ограничивают общий процесс Ollama на хосте**. Ollama совместно используется другими приложениями и не перенастраивалась глобально.

Тестовый запрос с полной схемой занял около 35 секунд. Это не гарантия средней скорости. Начальная очередь 400 сообщений может обрабатываться несколько часов; новые сообщения ждут в общей очереди. Точное повторение текста повторно использует результат в рамках tenant, версии парсера и digest модели. Скорость поступления может превышать скорость нормализации; состояние очереди следует контролировать.

## Проверки и границы доверия

- Строгая JSON-схема; неизвестные поля и незавершённая генерация отклоняются.
- Каждый извлечённый строковый фрагмент должен присутствовать в исходном тексте (регистр/пробелы нормализуются). Неподтверждённое поле обнуляется и помечается.
- Само наличие фрагмента не доказывает его правильную роль: модель может перепутать отправление и назначение, вид объявления или поля нескольких предложений.
- Вес переводится в кг, денежные суммы очищаются от разделителей тысяч, валюты определяются по явным обозначениям. Неизвестная валюта и неоднозначный `$` не превращаются автоматически в UAH/USD.
- Ставки за км/тонну маркируются отдельно и не принимаются за стоимость рейса.
- Дата нормализуется в ISO только из однозначной полной даты; для «завтра» дата не выдумывается.
- Геокодирование и перевод названий населённых пунктов не выполняются: сохраняются извлечённые названия, не добавляются выдуманные координаты.
- Классификация `load / vehicle / other / unknown` и признак нескольких объявлений — гипотезы модели.
- **Все результаты имеют `review_required=true` и `autopublish_allowed=false`.** Это не заявления об измеренной точности.
- В синтетическом примере правильно извлечены маршрут, вес, ставка и валюта, но модель ошибочно установила `multiple_ads=true` для одного предложения. Это подтверждает необходимость проверки перед автоматическими действиями.
- Пустые и слишком длинные сообщения отмечаются для проверки; текст не обрезается незаметно.

## Надёжность и доступ

- Постоянная очередь PostgreSQL; попытки, ошибки, задержки, версия парсера и digest модели сохраняются.
- Не более трёх попыток на ошибочную задачу, с задержкой; зависшие в `processing` задачи возвращаются в очередь после перезапуска.
- Advisory lock не допускает параллельный запуск второго нормализатора. Текущий worker последовательный.
- Отдельная роль БД `logistics_normalizer`: чтение сообщений и работа только со своими таблицами. Нет прав изменять исходные сообщения и грузы.
- Ollama и порт БД `15439` доступны только через loopback хоста. Порт БД не открыт в интернет.
- Worker не получает Telegram-сессию, GitHub-токен или SSH-ключ.
- В логах только ID задач, статус, длительность и класс ошибки; без исходных объявлений и ответов модели.

## Команды на сервере

```bash
cd /opt/logistics
docker compose -f deploy/compose.collector.yml logs --tail=30 normalizer
docker compose -f deploy/compose.collector.yml stop normalizer
docker compose -f deploy/compose.collector.yml up -d normalizer
```

Остановка normalizer не останавливает сборщик.

Состояние очереди:

```bash
docker compose -f deploy/compose.collector.yml exec -T postgres \
  psql -U logistics -d logistics -c \
  "SELECT status,count(*) FROM telegram_llm_jobs GROUP BY status;"
```

Секреты роли БД: `/etc/logistics/llm.env`, права 0600. Миграция `0004_local_llm.sql` применена отдельно к существующей базе. При переустановке нужно также создать ограниченную роль БД и защищённый env-файл; секреты не коммитятся.

## Проверки перед автоматизацией

Добавлены тесты структуры, нормализации, валют, единиц измерения, выдуманных полей, внешних endpoint и запрета неподтверждённых моделей. Качество на реальных данных ещё требует локальной ручной разметки и сравнения с regex-базой. Проверка JSON и цитат не исключает семантических ошибок модели.

Использовать контент только при наличии прав и разрешённых условий источников. Локальное размещение модели само по себе не отменяет условий Telegram/API и источников. Это отдельный opt-in режим обработки, не обучение модели.

Технический источник: https://docs.ollama.com/capabilities/structured-outputs
