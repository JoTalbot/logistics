# Пакетный разбор объявлений локальной LLM

## Действующий режим

`до 100 ожидающих задач → один локальный JSON-файл → один запрос /api/chat → проверка каждого ID → отдельная нормализация и запись каждого результата в PostgreSQL`

Сервис: `normalizer`. Модель: установленная локальная `qwen2.5:1.5b`. Сборщик Telegram продолжает работать независимо. Ранее успешно обработанные объявления не переобрабатываются только из-за включения пакетов.

### Ограничения пакета

- `LLM_BATCH_MAX_ITEMS=100` в защищённом `/etc/logistics/llm.env`.
- Контекст модели: 32 768 токенов. На момент проверки модель занимала около 2,3 GB; на сервере оставалось около 2,4 GiB доступной памяти при активной обработке.
- Пакет уменьшается по бюджету контекста: консервативная оценка входа по UTF-8 байтам, резерв 3000 токенов на инструкции/обрамление и 256 выходных токенов на объявление. Тексты не обрезаются.
- Максимум ответа: `max(1024, число_объявлений × 256)` токенов. Незавершённый ответ отклоняется, а не записывается как полный. Число выходных токенов может оказаться недостаточным для сложных объявлений; такие запросы имеют ограниченные повторные попытки.
- **«До 100» не означает, что любые 100 объявлений поместятся в один запрос.** Первый рабочий пакет после установки лимита 100 содержал 31 объявление.
- Пустые сообщения и сообщения длиннее 4000 символов помечаются для проверки, без отправки в модель. Точное совпадение текста может использовать ранее сохранённый результат без нового запроса.

## Файлы

На хосте: `/var/lib/logistics/llm-batches/<batch_uuid>.json`. В контейнере: `/batches/<batch_uuid>.json`.

```json
{
  "batch_id": "UUID",
  "announcements": [
    {"id": 101, "text": "текст первого объявления"},
    {"id": 102, "text": "текст второго объявления"}
  ]
}
```

ID — внутренний ID задачи БД; связь с Telegram source/message сохраняется в `telegram_llm_jobs.source_message_id`. В модель отправляется содержимое именно этого файла как один пользовательский JSON-вход. У модели нет инструментов чтения файлов или командной оболочки.

Каталог имеет права 0700, файлы — 0600. Они содержат исходный контент и не коммитятся. SHA-256 входного файла записывается в таблицу пакетов. Файлы удаляются обработчиком после 24 часов с момента завершения/прерывания пакета; при остановленном обработчике очистка возобновляется при его запуске.

## Формат ответа и сохранение

Для каждого входного ID схема ответа создаёт обязательный ключ:

```json
{"results": {"101": {"kind": "load", "origin": "…"}, "102": {"kind": "unknown", "origin": null}}}
```

Пример сокращён: реальная схема требует все поля `ExtractedAd`. Такой формат выбран после того, как модель вернула только один результат для трёх объявлений в первоначальной схеме с массивом.

- ID не сопоставляются по позиции в массиве.
- Дубли ключей, некорректная структура и незавершённая генерация отвергаются.
- Неизвестные ID не могут привязаться к чужому сообщению.
- Каждый извлечённый фрагмент проверяется только против **своего** объявления; фрагмент из соседней записи не считается подтверждением.
- Для корректного ответа выполняются существующие нормализация веса, суммы, валюты, даты и проверка источника полей.
- Каждый результат отдельно коммитится в `telegram_llm_jobs.normalized`; `batch_id` связывает его с запросом.
- Ошибка отдельного ответа не отменяет уже сохранённых соседних результатов. Только отсутствующие/ошибочные задачи возвращаются в очередь, не более трёх завершившихся ошибкой попыток.
- Повторная попытка формирует новый файл и новый пакет. У каждого файла ровно один вызов inference; счётчик в БД обозначает отправку запроса, а не гарантированную доставку при сетевом сбое.
- После прерывания процесса незавершённые задачи возвращаются в очередь без штрафа к лимиту ошибок; ранее сохранённые не повторяются. Прерванный пакет отмечается отдельно.

**Нормализованный результат остаётся кандидатом для проверки.** Сохранены `review_required=true` и запрет автоматической публикации. Структурная корректность и наличие цитаты не доказывают правильную интерпретацию маршрута или цены; модель может смешивать смысл даже при правильных ID.

## Аудит в PostgreSQL

Новая таблица `telegram_llm_batches`: ID, число объявлений, файл и хеш, digest модели, статус, счётчик отправки, число сохранённых/ошибочных ответов, длительность. Миграция `0005_llm_batches.sql` применена; ограниченной роли выданы права только на работу с этой таблицей. Права на изменение `loads` не выдавались.

```bash
cd /opt/logistics
docker compose -f deploy/compose.collector.yml logs -f --tail=20 normalizer

docker compose -f deploy/compose.collector.yml exec -T postgres \
  psql -U logistics -d logistics -c \
  "SELECT item_count,request_count,status,completed_count,failed_count,duration_seconds FROM telegram_llm_batches ORDER BY created_at DESC LIMIT 10;"
```

`telegram_llm_jobs.duration_seconds` для пакетного режима — распределённое время пакета на элемент, а не отдельное измерение inference для объявления. Полная длительность хранится в `telegram_llm_batches`.

## Что проверено

- **35 тестов прошли**, 4 интеграционных теста прежнего набора пропущены.
- Тесты: лимит 100, уменьшение по контексту без обрезки, один HTTP-вызов на файл, сопоставление по ID, пропуски/дубли/посторонние ID, запрет подтверждения полей чужим объявлением.
- Реальный пакет из **3 объявлений**: **1 запрос**, **3 отдельно сохранённых результата**, около **139,5 секунды**. Это не подтверждает точность значений и не показывает ускорения по сравнению с одиночной обработкой.
- После проверки включён лимит **100**; фактический следующий пакет содержит **31 объявление** и на момент фиксации ещё обрабатывается. Завершение большого пакета и качество на нём пока не подтверждены.

Пакетный режим сокращает число запросов, но не гарантирует ускорение маленькой CPU-модели. Большой пакет может занимать много минут; таймаут одного inference — 1800 секунд. При систематических таймаутах следует уменьшить лимит и оценить качество/производительность, а не бесконечно повторять огромные пакеты.
